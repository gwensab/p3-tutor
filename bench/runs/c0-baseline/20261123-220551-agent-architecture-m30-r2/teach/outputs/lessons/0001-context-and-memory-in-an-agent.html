Context and memory in an agent

By the end of this lesson you can decide, for each piece of information in the makerspace assistant, whether it belongs in the context, in saved notes, or in a searchable manual, and say why.

Objective O3: context and memory in an agent About 30 minutes Builds on your work on the agent loop (quiz 0001)
Why this matters for you

Your assistant must answer from long machine manuals, remember each student's training status between visits, and stay inside a small model budget. All three come down to one design question: what does the model see on each call, and what is stored somewhere else until it is needed? That is the question your design review will ask.

The context window 5 min

Start with a concrete case. A student types: "Is the laser cutter free tomorrow at 3 pm, and do I need training to use it?" The model must answer this. What can it use?

Only the text it is handed on that call. The model has no view into your booking system, no copy of the manuals, and no recollection of other students. Everything it can use sits in one block of text the program assembles and sends. That block is the context: all the tokens the model reads when it produces its next output. A token is a small chunk of text, roughly three-quarters of an English word on average, and it is the unit models read, write and are billed in.

The context window is the limit on how much the model can handle at once. Anthropic's documentation describes it as the model's working space: the conversation history plus the new output the model writes, together, must fit within the window (Claude Platform Docs, Context windows). Think of a workbench. Only what is on the bench can be used for the job in front of you, and the bench has a fixed size.

Two consequences matter right away.

The window is a hard limit. If the parts add up to more than the window, the call fails or something must be dropped. The limit differs by model, and current sizes are listed in the official docs, so look them up there instead of memorising a number.

A big window is not a free pass. Anthropic's engineering team describes context as a finite resource with diminishing returns: as the number of tokens grows, the model's ability to recall details from it tends to fall, an effect they call context rot, because the model has a limited "attention budget". Their guidance is to find the smallest set of high-signal tokens that makes the right answer likely (Anthropic, Effective context engineering for AI agents). Cost points the same way, as the next section shows.

A common mix-up

"With a window big enough for a whole textbook, I can paste all the manuals in and be done." It is tempting because it is simple and often works in a demo. It goes wrong in two ways: every call then carries and pays for all those tokens, and the model has to find one relevant paragraph in a haystack, which it does less reliably as the haystack grows. A big window raises the ceiling. It does not tell you what to put under it.

What is kept between steps 5 min

Last time you saw that each step of the loop is a separate model call. Here is what that means for memory: the model does not carry anything from one call to the next. Each call starts blank, and the program makes the steps feel connected by sending the whole conversation again every time. This is how the models are used through an API, and the docs describe the conversation history as the input that is built up turn by turn (Claude Platform Docs).

In Python terms, the program keeps a list. Here is the shape of it, simplified:

messages = [{"role": "user", "content": "Is the laser cutter free tomorrow at 3 pm?"}]

while True:
    reply = call_model(system_prompt, tools, messages)   # model reads ALL of messages
    messages.append(reply)                               # keep what the model said
    if reply is a final answer:
        break
    result = run_tool(reply)                             # the program runs the tool
    messages.append(result)                              # keep what came back

The messages list is the memory between steps. It lives in your program, and the model sees it only because you pass it in on every call. Nothing else is remembered.

Worked example: what a request costs

The student asks the question about the laser cutter and training. Suppose the system prompt and tool descriptions together are 1,000 tokens and the question is 30 tokens. The model asks for three tools in turn; each request it writes is 40 tokens, and the results are 200 tokens (calendar), 3,000 tokens (manual passage) and 100 tokens (training record). Count the tokens the model reads on each call.

  1. Call 1: system and tools 1,000 + question 30 = 1,030 tokens read.
  2. Call 2: everything from call 1, plus the model's 40-token request, plus the 200-token calendar result: 1,030 + 40 + 200 = 1,270.
  3. Call 3: 1,270 + 40 + 3,000 (the manual passage) = 4,310.
  4. Call 4, which writes the final answer: 4,310 + 40 + 100 = 4,450.
  5. Add them: 1,030 + 1,270 + 4,310 + 4,450 = 11,060 tokens read, although the conversation ends at about 4,450 tokens.

The lesson in the numbers: input is read again on every call, so a big tool result is paid for on every later call, not once. The 3,000-token manual passage was read twice here (calls 3 and 4). In a 12-step run it would be read nine times.

Providers offer prompt caching, which lowers the price of re-reading an unchanged start of the context. It helps, but it does not remove the lesson: a smaller context is still cheaper and easier for the model to use. Check your provider's pricing page for the current terms.

When the window fills up 4 min

The history grows with every step. A long troubleshooting chat with a student, or an agent reading many manual pages, can approach the limit, or just become expensive and muddled long before it. Your program can manage the list, and Anthropic's guidance on context engineering names the main moves (Anthropic, Effective context engineering):

  • Trim old tool results. Once the model has used a 3,000-token manual passage to answer, the passage rarely needs to stay. Replace it with a one-line stub, such as "searched laser manual, section 4.2". This is often the cheapest and safest move.
  • Summarize. Replace the early part of a long conversation with a short summary written by the model, and continue from there. You lose detail, so keep in the summary what later steps need: decisions made, facts confirmed, what is still open.
  • Drop the oldest messages. Simple, but it can drop the very fact that mattered, such as the machine the student said they wanted at the start. Use it only when the early part is not needed.
  • Move information out of the context into notes or a searchable store, and fetch it when needed. The next two sections cover this.

Each move trades something: trimming and dropping lose detail for good, and summarizing might lose the wrong detail. There is no free option, so the design question is what the model will need later.

A common mix-up

"If it is in the conversation, the assistant will remember it." Only while it is still in the context. Once your program trims, summarizes or drops it, the model has no trace of it, and it will not say so; it may answer confidently from what is left. This echoes something you noticed about chatbots: they can state wrong things with confidence. Missing context is one cause.

What is kept between sessions: notes 5 min

A session is one conversation, from the first message to the end. When it ends, the messages list is gone, unless your program saves it. A new session starts with an empty context. So by default the model keeps nothing between sessions: it will not know that a student finished laser training last week.

The fix is to write what matters somewhere outside the context, and read it back in when a new session starts or when it is needed. Call this notes, or long-term memory. Lilian Weng's widely cited overview of LLM agents makes the same split: the context is the agent's short-term memory, and long-term memory is an external store the agent can keep and recall from (Weng, LLM Powered Autonomous Agents). Anthropic describes the same idea as structured note-taking: the agent writes notes to storage outside the context window and pulls them back in later (Anthropic, Effective context engineering).

For you this can be plain Python: a JSON file or a small database table.

{
  "student_id": "s1042",
  "training": {"laser_cutter": "completed 2026-10-14", "3d_printer": "not started"},
  "note": "prefers morning slots"
}

There are two ways to connect it to the agent:

ApproachHow it worksGood for
Load at startThe program reads the student's record when the session opens and puts it into the context.Small facts needed almost every time
ToolsYou give the model get_training_record and save_note tools, and it decides when to read or write.Larger or rarely needed information

Notice that notes are just more tools, so the loop you already know covers them. Notice also a decision hiding here: what is worth saving. Saving the whole chat brings back the size problem. Saving a few facts, such as a training status or a stated preference, keeps the next session small. And training status should not be a model-written note at all: it should come from a trusted record, because a note a model wrote from a student's claim ("I finished training") is only as reliable as the claim.

A common mix-up

"Modern assistants remember me, so mine will too." Some products add memory features, but that is the product's program saving and reloading text, exactly as above. The model itself starts every call blank. If you want your assistant to remember, you build the saving and the loading.

Retrieval: finding the right page 5 min

Now the manuals. Suppose the laser cutter manual is 120 pages, perhaps 80,000 tokens, and there are twelve machines. Pasting all of them into every call would be huge and slow, and by the cost arithmetic above you would pay for it on every step. The alternative is retrieval: keep the manuals outside the context, and when a question comes, find the few passages that bear on it and put only those into the context.

A common design has these steps:

  1. Prepare once, ahead of time. Split each manual into chunks, passages of a few paragraphs each, ideally cut at section boundaries so a chunk makes sense alone. Store each chunk with its machine name and section title.
  2. Search at question time. Turn the question into a search over the chunks and take the top few matches. The simplest search is keyword matching. A more powerful one compares the meaning of the question and the chunks using numbers called embeddings; you can start with keywords and upgrade when it fails.
  3. Return a few chunks to the model as a tool result, with their source labels, so the model can answer from them and cite the page.

The agent can do the searching itself through a search_manuals(machine, query) tool: that is the same loop you know, with retrieval as a tool. Anthropic calls the pattern of fetching information on demand, instead of loading it all in advance, just-in-time retrieval, and notes that it keeps the context small and lets the agent explore step by step (Anthropic, Effective context engineering).

Worked example: one question, retrieved

"What material can't I put in the laser cutter?"

  1. The model calls search_manuals(machine="laser cutter", query="prohibited materials").
  2. The search ranks that manual's chunks and returns the best three, about 600 tokens in all, each labelled with its section, such as "Section 2.3 Materials: never cut PVC or vinyl".
  3. The model writes the answer from those chunks and names the section.
  4. Cost: 600 tokens of manual in the context instead of 80,000, and the model had far less to wade through.

Retrieval can fail, and you should know how, since your design review may ask. If the search returns the wrong chunks, the model answers from the wrong text, or says it cannot find the answer. Typical causes are chunks cut mid-thought, a question worded differently from the manual ("fumes" versus "ventilation"), and too few results. When you build it, test the search by itself first: for ten real student questions, does the right passage appear in the top three?

Worked example and practice 4 min

Worked example: where does it live?

Take the item "the booking calendar for next week" and decide among three homes: context (loaded on each call), notes (saved facts about a student or session), retrieval (a searchable store that is queried).

  1. Ask how big it is. A week of bookings for all machines could be hundreds of entries: too big to carry on every call.
  2. Ask how often it is needed. Only when a student asks about availability: not every call.
  3. Ask whether it changes. Constantly. Anything saved as a note would go stale, so it must be read fresh.
  4. Decide. It does not belong in the context or the notes. Read it live through check_calendar, so only the answer for the one machine and day enters the context. The live tool is the right home, not a copy.

Summary 1 min

  • The model sees only the context of the current call. The window limits its size, and a bigger window does not mean a better answer.
  • Between steps, memory is the messages list your program keeps and resends, so every call re-reads it and the cost adds up. Trim, summarize or drop when it grows.
  • Between sessions, nothing survives unless you save it. Notes are saved facts, read back by the program or by tools.
  • Retrieval keeps big documents outside the context and fetches only the few relevant chunks.
