Context and memory in an agent

By the end of this lesson you can decide, for each piece of information in the makerspace assistant, whether it belongs in the context window, in saved notes, or in a manual that is searched on demand, and say why.

Objective O3: context and memory in an agent About 30 minutes Builds on the agent loop (quiz 0001)
Why this matters for you

Your assistant must answer from long machine manuals and remember each student's training status between visits, all on a small budget. Those three jobs are three different kinds of memory, and each has a different cost. At your design review you will need to say which job goes where, and defend it.

Warm-up 2 min

Two questions from the agent loop. Answer in your head or on paper first, then open the answer.

Recall

When the model decides it needs the booking calendar, what does it actually produce, and what part of the system then runs the tool?

Check your answer

The model produces text: a request naming the tool and its arguments, such as check_calendar("laser cutter", "Friday"). It does not run anything. The program around the model runs the tool and puts the result back in front of the model.

Recall

In the loop, the program gives the model something at every step. What is it, and what makes the loop stop?

Check your answer

It gives the model the conversation so far, now including the latest tool result. The loop stops when the model writes a final answer instead of a tool request, or when the program hits a limit such as a step cap.

Today we open up that phrase, "the conversation so far". It turns out to be the whole story of memory in an agent.

The context window 5 min

Start with an example

Imagine you hire a helper who has total amnesia every time you leave the room. Each time you come back, you must hand them a printed folder: the house rules, the list of tools, and everything said so far. They read the whole folder, write the next reply, and forget everything the moment they finish. The folder is the only thing they know.

That helper is a language model, and the folder is its context.

The general idea

The context is the set of tokens the model is given when it writes its next output. A token is a small chunk of text, often a short word or part of a word. The context window is the limit on how many tokens the model can handle at once. The Anthropic documentation describes the window as all the text the model can reference when generating a response, including the response itself, and calls it working memory, not training data (Context windows, Claude docs).

What counts toward it? Everything the model reads or writes: the system prompt (the standing instructions you write), the descriptions of your tools, every message, every tool result, and the model's own replies (Claude docs). If the input alone is too long, the request is refused.

Two facts follow, and the rest of the lesson builds on them.

  1. The model has no memory of its own between calls. Whatever is not in this call's context does not exist for it. Something the model "remembers" is something the program put back in.
  2. Bigger is not simply better. The docs say more context is not automatically better, and name context rot: accuracy and recall get worse as the number of tokens grows. Anthropic's engineering team describes it as an attention budget: every new token uses some of it, so the goal is the smallest set of high-signal tokens that gets the job done (Effective context engineering for AI agents).
Check yourself

A student told the assistant in step 1 that they are left-handed. At step 4 the model correctly uses that fact. Where did the model get it?

Show the answer

The third option. The program sends the earlier messages along with each new call, so the fact is in the context. The model has no other place to get it.

What is kept between steps 6 min

Start with an example

A student asks: "Is the laser cutter free Friday at 3, and do I need training?" Here is the loop, with what the program sends to the model each time.

CallWhat the model receivesWhat it writes
1Rules + tools + the questionRequest: check_calendar
2Everything in call 1 + that request + the calendar resultRequest: check_training_record
3Everything in call 2 + that request + the training resultFinal answer

Each row contains the one above it. The context only grows. The Claude docs say the same in general terms: previous turns are preserved completely, each turn's input holds all the earlier history plus the new message, and the output becomes part of the next turn's input (Claude docs).

So what is "kept between steps" is simply the growing list of messages: the question, each tool request, each tool result. The program keeps that list and resends it. Nothing is kept inside the model.

Why it matters for your budget

Model usage is billed in tokens, and the input you send on every call counts. Even the old history you resend is input: the docs note that prompt caching "changes what you pay for those tokens, not whether they count" (Claude docs). So the cost of a request is not the size of the final context. It is the sum of the context sizes of every call, and that sum grows faster than the number of steps. A 10-step request costs much more than twice a 5-step one.

Caching can make resent tokens cheaper, which is worth asking about when you build. It does not change the lesson: a smaller context is still cheaper and still more accurate.
A common mix-up

"The model remembers the earlier steps, so resending them is just wasteful." It is tempting because a chat feels like a continuous conversation. But the continuity is made by your program. If it sent only the newest tool result, the model would not know what the student asked. The fix for cost is not to stop resending; it is to keep what is resent small and useful.

Check yourself

Your assistant's search_manuals tool returns three full manual pages (about 6,000 tokens) into the context at step 2 of a 6-step request. What is the effect on cost?

Show the answer

The third option. A large tool result is carried forward and resent on every call after it, so its cost is multiplied by the number of calls left in the request.

When the window fills up 5 min

Because context only grows, a long task can hit the limit, or become costly and unreliable well before it. Anthropic describes three tidying moves; each one gives up a little detail to make room (Effective context engineering).

  • Clearing old tool results. Once the model has used a tool result, the raw output deep in the history is rarely needed again. Anthropic calls this one of the safest, lightest-touch forms of tidying. Example: after the assistant has read the calendar and decided, drop the 40 lines of calendar data and keep the decision.
  • Compaction. When the conversation nears the limit, ask the model to summarize it, then start a fresh context holding the summary. A good summary keeps decisions and open problems and drops redundant tool output.
  • Notes outside the window. Write important facts to storage, so they survive any clearing or summarizing. This is the next section.

Compaction and clearing are available as features in Anthropic's API, but you could also write either yourself in a few lines of Python: replace old items in your message list.

A common mix-up

"A bigger window solves memory." A bigger window raises the limit, but not the cost or the context rot, and it empties when the session ends. A 1,000-page manual pasted into every call is both expensive and harder for the model to use well. You will see the better answer in the retrieval section.

What is kept between sessions: notes 6 min

Start with an example

Think of a mechanic's shift handover. The day mechanic does not hand over their memory. They write a log: "Press 2 is down, waiting on part; Dana is cleared for the lathe." The night mechanic reads the log first. The log survives because it is on paper.

A session is one run of the assistant, from a student's first message to the end of the conversation. When it ends, the context is thrown away. A student who returns next week meets a model with a completely blank folder. So anything that must last is written to storage the program owns: a file, a database row, a JSON record.

Anthropic calls this structured note-taking: the agent regularly writes notes to memory outside the context window and pulls them back in later (Effective context engineering). Their memory tool is one version of it. Claude can create, read, update and delete files in a /memories directory, but the program does the actual file operations: "Claude requests file operations, and your application runs them." That is the agent loop again, with a file tool (Memory tool, Claude docs).

Here is what your assistant's memory for one student might look like. This is a design sketch for your team, not required code:

{
  "student": "dana-k",
  "trained_on": ["laser cutter", "3D printer"],
  "pending": "lathe safety session booked for Nov 30",
  "preferences": "prefers evening slots"
}

At the start of a session, the program loads this record into the context (a few dozen tokens). At the end, or when something changes, it is updated. The model never needs the whole history of Dana's visits, only this.

Decide what to write down

Notes are only as good as what you chose to save. A useful test: would the assistant be worse off next session without this? Training status, yes. The exact wording of a greeting, no. Also decide who is allowed to change a note. The docs list safeguards your program must own: restrict file access to the memory folder, cap file sizes, strip sensitive data, and expire stale notes (Memory tool docs). For the makerspace, a student's training status should probably be read from your official training records, not from a note the model wrote, because a wrong note would unlock a dangerous machine.

Check yourself

Which fact should the assistant save to notes for next week?

Show the answer

The third option. Good notes are small, specific to the user, and useful later. One-off questions go stale, and shared reference text belongs in retrieval, not notes.

Retrieval: finding the right page 6 min

Start with an example

You do not read a whole textbook to answer one exam question. You use the index, jump to the page, and read that page. A 400-page set of machine manuals should work the same way for the assistant.

Retrieval means fetching only the relevant pieces of a large body of text into the context when they are needed, instead of keeping everything there. Anthropic's engineering team calls this just-in-time loading: the agent keeps lightweight pointers, such as file paths or stored queries, and uses tools to load data when needed (Effective context engineering). In your assistant, that is the search_manuals tool you already know.

A typical build has three parts:

  1. Chunk the manuals into small passages, such as a section or a few paragraphs each.
  2. Index them so they can be searched, by keyword matching, by meaning (embeddings, which turn text into numbers so similar meanings are close), or both.
  3. Search at question time: the model calls search_manuals("laser cutter max acrylic thickness"); the program returns the top few chunks; only those enter the context.

Retrieval fails in a specific way

If the search returns the wrong chunk, the model may answer confidently from it. Chunks lose context when cut out: a passage saying "the maximum thickness is 6 mm" does not say which machine it is about. Anthropic's Contextual Retrieval technique prepends a short, chunk-specific explanation to each chunk before indexing; in their tests, combined with keyword search, it cut the failure rate of finding the right chunk in the top 20 results by 49% (5.7% to 2.9%) (Contextual Retrieval, Anthropic). A simpler version you can do by hand: put the machine name and section title at the start of every chunk.

Your team will meet the term RAG, "retrieval-augmented generation": retrieve first, then have the model write the answer from what was retrieved. It is the same idea as the search tool above.
A common mix-up

"Retrieval means the model searches its own memory." It does not. Retrieval is a tool your program provides, over a store you built. If a manual page is not in your index, the model cannot find it, and it may fill the gap with a confident guess. You have seen this in chatbots that state outdated facts: the model's training is not a searchable, current store.

Check yourself

A student asks how to change the blade on the bandsaw. Which design is best for cost and accuracy?

Show the answer

The second option. Retrieval loads only what is needed, so the question is answered from your real manual at low token cost.

Worked example and practice 5 min

Now put the three kinds of memory together on a number. First, how to estimate a request's input cost.

Worked example

The system prompt, tool descriptions and question take 3,000 tokens. Each tool step (request plus result) adds 1,000 tokens. The model uses 2 tools, then writes its final answer. How many input tokens are processed in total?

  1. Count the calls: one per tool request, plus one for the final answer. That is 3 calls. (Each call is a separate trip to the model.)
  2. Find each call's input. Call 1 has only the start: 3,000. Call 2 adds step 1: 4,000. Call 3 adds step 2: 5,000.
  3. Add them: 3,000 + 4,000 + 5,000 = 12,000 input tokens, even though the final context is only 5,000.
  4. Now see what retrieval does. If one of the steps had pasted a 6,000-token manual instead of a 1,000-token chunk, every later call would carry 5,000 extra tokens. That is the saving from retrieving small chunks.
Your turn

The start is 2,000 tokens and each tool step adds 500 tokens. The model uses 3 tools and then answers. Step 1 is given: there are 4 calls. Find each call's input, add them, and then say which memory type you would use for a student's training status.

Show a solution

Calls: 2,000 + 2,500 + 3,000 + 3,500 = 11,000 input tokens. Training status goes in saved notes (or better, is read from the official record by a tool): it is about one student, it must outlive the session, and it is small. The manuals go through retrieval; the loop's own messages live in the context.

Summary 2 min

  • The model only knows what is in its context window this call; the program resends the history at every step, so context grows and every call pays for all of it.
  • When context gets big, clear old tool results, compact into a summary, or move facts into notes.
  • Between sessions, only what the program saved survives: small notes about the user, written and loaded by your code or a memory tool.
  • For long manuals, keep them in storage and retrieve a few chunks on demand; poor chunks cause confident wrong answers.
