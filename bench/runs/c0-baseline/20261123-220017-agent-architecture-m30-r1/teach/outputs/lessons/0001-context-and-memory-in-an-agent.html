Context and memory in an agent

By the end of this lesson you can decide, for each piece of information in the makerspace assistant, whether it belongs in the model's context, in a saved note, or in a manual you search, and say why.

Why this matters for you

Check your answer

The program around the model runs the tool. It then puts the result into the model's next input and calls the model again. That second part is today's topic: "the model's next input" is the context, and what goes into it, and what stays out, is the whole story of memory in an agent.

The context window 5 min

Start with a concrete picture. A student walks up and asks your assistant, "Can I use the laser cutter on Friday afternoon?" The model does not see the student, the booking system or the manuals. It sees one thing: a block of text the program hands it for this call. That block is the model's context: everything the model can read when it writes its next reply.

For the makerspace assistant, that block holds these parts:

  • the system prompt: your standing instructions ("You are the makerspace assistant. Never book a machine without checking training.");
  • the tool descriptions: the name, purpose and parameters of each tool, which you met in the last lesson;
  • the conversation so far: the student's messages and the model's earlier replies;
  • the tool results: whatever each tool call returned, such as calendar rows or a manual page.

The context window is the maximum amount of text the model can take in per call, counting both its input and what it writes. Text is counted in tokens: small chunks of text, often a short word or part of a longer word. A rough rule for English is that 100 tokens is about 75 words. Anthropic's documentation describes the context window as the model's working memory for the conversation, and notes that it is a different thing from the large body of text the model was trained on (Claude docs: context windows).

Two facts follow, and both matter for your budget. First, the model only knows what is in the box: if a fact is not in the context, the model cannot use it, however true it is. Second, you pay by the token for the box, not for the question alone, so a long manual page in the context costs money every time it is sent.

A common mix-up

"A bigger window means the model reads everything in it equally well." It is tempting because a bigger number sounds like a bigger brain. But a larger window only raises the limit on how much fits. Research on long inputs found that models do worst when the relevant fact sits in the middle of a long context, and best when it is near the start or the end, even for models built for long inputs (Liu et al., "Lost in the Middle"). Anthropic's engineering team calls the related effect context rot: as the number of tokens grows, the model's ability to recall information from the context falls (Effective context engineering for AI agents). So "fits" and "is used well" are different questions.

What is kept between steps 6 min

Now connect this to the loop. You learned that each step of an agent is a separate model call. Here is the consequence: the model does not carry anything over from one call to the next. Each call starts blank, and the program makes it feel continuous by sending the whole history again. The model's "memory" within a task is the list of messages the program keeps and re-sends. (This is how the chat interface of the API works: you pass the full list of messages each time, according to the context window docs.)

That figure comes from a request you will see worked out in full later in this lesson. The shape is the point: the input grows with every step, so a long loop costs much more than the sum of its parts. This is why a step limit, from the last lesson, is also a budget tool.

Providers offer discounts for input that repeats exactly from one call to the next, called prompt caching. It can cut the cost of re-sending a long history, but it does not change what the model sees. Check your provider's current rules before you build a budget around it.

Notice what the program chooses to keep. It could keep every tool result in full, or it could keep a short version. The loop does not force full history; that is a design decision, and it is yours.

When the context gets too full 5 min

Because the context only grows, two things eventually go wrong: it can hit the window limit, and, before that, quality and cost suffer. Anthropic's guidance is to treat context as a limited resource and aim for the smallest set of high-signal tokens that still gets the job done (Effective context engineering for AI agents). Three ways to do that are common:

TechniqueWhat it doesMakerspace example
Clearing old tool resultsDrops bulky results the model has already used.After the model has read the laser cutter's calendar, replace the 40 calendar rows with "checked: free 2 to 4 pm".
Summarizing (also called compaction)Replaces a long history with a short summary and carries on.After a long chat about a project, keep a five-line summary of what the student wants.
Returning lessDesigns each tool to return only what is needed.A calendar tool takes a date and returns that day's free slots, not the month.

The third is the cheapest, since the data never enters the context. Anthropic's post also says tools should be token-efficient, returning information that is useful and no more. Clearing and summarizing both lose detail, so they are a trade: you save tokens and risk throwing away something the model needs later.

The second option. Returning less keeps the data out of the context entirely, so it is the cheapest fix.

What is kept between sessions: notes 6 min

Everything so far lives inside one task. A session here means one conversation or task from start to finish. When it ends, the program drops the message list. The next time a student shows up, the context starts empty. So the assistant has no idea that this student finished laser cutter training last week, unless something outside the context remembers it.

A common mix-up

"The model learns from each conversation and remembers the student next time." It is tempting because chat products can feel like they remember you. But the model's built-in knowledge is fixed from training and does not change when you use it. Any memory that lasts across sessions is something the program saves and later puts back into the context.

The simplest design is notes: facts written to storage outside the model, such as a file or a database row, and read back when needed. Anthropic's memory tool works this way. It lets the model store and retrieve information across conversations through file operations that your own application carries out, so the memory lives in your storage (Claude docs: memory tool). That matches what you learned about tools: the model asks, the program acts.

For the makerspace assistant, a student's note might look like this:

students/jlee.json
{
  "trained_on": ["laser_cutter", "3d_printer"],
  "training_date": {"laser_cutter": "2026-10-02"},
  "prefers": "evening slots"
}

At the start of a session, the program (or a tool call) loads this note into the context. At the end, or when something changes, it writes the note back. Two questions decide every note design:

  • What is worth saving? Facts that stay true and that the next session will need: training status, preferences. Not the full chat, which is long and mostly stale.
  • Who writes it? For training status, the training system is the authority, so your assistant should read it, not trust a note the model wrote itself. A model-written note can be wrong, and a wrong note repeats forever.

Retrieval: finding the right page 6 min

The machine manuals are the other memory problem. A laser cutter manual may run to hundreds of pages, and you have many machines. Pasting all of it into every context would be slow, costly and, as you saw, poorly used. The fix is retrieval: keep the manuals outside the context, and bring only the few relevant pieces in when a question needs them.

The usual steps are:

  1. Prepare once. Split each manual into chunks, short passages such as one section or a few paragraphs, and store them in a way that can be searched.
  2. Search per question. Given the student's question, the search returns the few best-matching chunks. The search can match on words, on meaning, or both.
  3. Put the best chunks in the context. The model answers from them, and your tool can return their source page so the answer can be checked.

In an agent, retrieval is simply a tool: search_manuals(machine, query). The model decides when to call it, which fits Anthropic's advice that agents can load data at runtime with tools instead of putting everything in the context in advance (Effective context engineering for AI agents). Retrieval and notes share one idea: memory is storage outside the context plus a way to bring the right piece in.

Retrieval can fail in two ways, and you should watch for both. The search may return the wrong chunk, so the model answers from the wrong page. Or the chunks may be cut so that the answer is split across two of them. A good design returns the source page with each chunk, so a wrong answer can be traced.

Worked example and practice 7 min

Worked example: what does one request cost in input tokens?

A student asks: "Is the laser cutter free tomorrow at 3 pm, and do I need training?" The system prompt plus tool descriptions plus the question total 1,550 tokens. The model asks for check_calendar (60 tokens out); the result is 400 tokens. Then it asks for search_manuals (80 tokens out); the result is a 3,000-token manual page. Then it asks for check_training_record (100 tokens out); the result is 150 tokens. Then it writes the answer (120 tokens out). How many input tokens are sent over the four calls?

  1. Call 1. The input is the starting context: 1,550 tokens.
  2. Call 2. The input is call 1's input plus the model's first request plus the calendar result: 1,550 + 60 + 400 = 2,010.
  3. Call 3. Call 2's input plus the second request plus the manual page: 2,010 + 80 + 3,000 = 5,090.
  4. Call 4. Call 3's input plus the third request plus the training result: 5,090 + 100 + 150 = 5,340.
  5. Total. 1,550 + 2,010 + 5,090 + 5,340 = 13,990 input tokens. The new text in the whole request is only about 5,500 tokens, so history re-sending costs well over twice that.
Your turn

Same request, but a better search_manuals returns only a 1,000-token chunk instead of 3,000. Everything else is the same. Calls 1 and 2 are unchanged (1,550 and 2,010). Work out call 3, call 4 and the total input tokens.

Show a solution

Call 3: 2,010 + 80 + 1,000 = 3,090. Call 4: 3,090 + 100 + 150 = 3,340. Total: 1,550 + 2,010 + 3,090 + 3,340 = 9,990 input tokens. Cutting the manual chunk by 2,000 tokens saved about 4,000 input tokens in total, because the chunk was re-sent in both calls 3 and 4. The earlier a big result enters the context, the more times you pay for it.

Summary 3 min

  • The model knows only what is in its context, and the program decides what goes in.
  • Between steps, the program re-sends the history, so input and cost grow with every step.
  • A bigger window is not better use: keep context small and high-signal, and have tools return less.
  • Between sessions, nothing persists unless the program saves it as notes and loads it back.
  • Retrieval keeps long documents outside the context and brings in only the best chunks.
