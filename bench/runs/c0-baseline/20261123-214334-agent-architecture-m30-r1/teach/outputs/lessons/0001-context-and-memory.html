Context and memory in an agent

By the end of this lesson you can decide, for each piece of information in the makerspace assistant, whether it belongs in the context window, in saved notes, or in a searchable manual.

Warm-up 2 min

Before the new material, one question from the agent loop. Answer it in your head first.

Recall

The model has asked for the tool check_calendar. Who actually runs it, and what happens to the result?

Check your answer

The program around the model runs the tool. It then puts the result into the model's next input and calls the model again. That last part is today's topic: "the model's next input" is the context, and what goes into it, and what stays out, decides how well and how cheaply your assistant works.

The context window: what the model sees 6 min

Start with an everyday case. You ask a friend to answer your question over the phone, but your friend can only use a single sheet of paper that you hand over before the call. Anything not on the sheet does not exist for them. That sheet is the model's situation on every call.

A token is a small chunk of text, often a word or part of a word; models read and write in tokens, and usage is counted and billed in tokens. The context is "the set of tokens included when sampling from a large-language model" (Anthropic, context engineering). The context window is the limit on how much the model can reference in one call, "including the response itself" (Claude docs, context windows).

For your assistant, the sheet of paper holds more than the student's question:

  • the system prompt: your standing instructions ("you are the makerspace assistant, never book without checking training");
  • the tool descriptions: the names, purposes and parameters from your earlier session;
  • the conversation so far: the student's messages and the assistant's replies;
  • the tool requests and tool results: every calendar answer and manual excerpt that came back.

The Claude docs state that the system prompt, messages and tool definitions all count toward the window.

A common mix-up

"The model knows what it has seen before, like a person does." It does not. Between calls the model keeps nothing. If a fact is not in this call's context, the model cannot use it, however many times it appeared in earlier calls. This is tempting because chat apps feel continuous; they feel that way because the program sends the earlier messages again each time (next section).

Between steps: everything is sent again 6 min

In the agent loop each step is a separate model call, and the model keeps nothing between calls. So how does step 3 know what step 2 found? The program sends the whole history again. The Claude docs say each turn's input "contains all previous conversation history plus the current user message" (context windows).

Think of a relay where the baton gets heavier at every handoff: each new tool result is added to the baton, and the next runner carries it all. This matters for your budget, because you pay for input tokens on every call (the docs add that prompt caching "changes what you pay for those tokens, not whether they count").

Worked example: counting what you pay for

Illustrative numbers, not real measurements. The system prompt plus tool descriptions plus the student's question come to 1,550 tokens. Each tool result adds 800 tokens. The request uses three tools, so there are four model calls. We ignore the model's own short tool requests.

  1. Call 1 reads 1,550 tokens.
  2. Call 2 reads 1,550 + 800 = 2,350.
  3. Call 3 reads 2,350 + 800 = 3,150.
  4. Call 4 reads 3,150 + 800 = 3,950.
  5. Total input read: 1,550 + 2,350 + 3,150 + 3,950 = 11,000 tokens, almost three times the 3,950 in the final context.

The lesson for design: a tool that returns a whole manual chapter (say 8,000 tokens) is expensive twice over. It costs 8,000 tokens the moment it arrives, and it is carried and paid for on every later call.

When the window fills up 5 min

Two different problems appear as the context grows.

Problem one: a hard limit. If the input alone exceeds the window, the API returns an error ("prompt is too long"); nothing is silently cut (context windows). Your program has to manage the context before that happens.

Problem two: a soft limit, often reached first. Anthropic describes context rot: "as the number of tokens in the context window increases, the model's ability to accurately recall information from that context decreases," because the model has a limited "attention budget" and "every new token introduced depletes this budget" (context engineering). The aim is "the smallest set of high-signal tokens" that gets the job done. So a bigger window is not a free upgrade: you still pay for every token, and more of them can make the model worse at finding the one that matters.

Two ways to shrink a context that has grown, both from the same article:

  • Tool result clearing: remove old tool results that are no longer needed, the "lightest touch" way. The booking calendar answer from ten steps ago can go once the booking is made.
  • Compaction: when a conversation nears the limit, summarize it and start a new context with the summary, keeping decisions and open problems and dropping redundant output.

Both lose detail. Anything you may need exactly later (a booking reference, a safety rule) should be kept, or saved outside the context, which is the next topic.

A common mix-up

"With a huge window I can paste every manual in and skip the clever parts." It is tempting because it removes work. But with the manuals in context you would pay for them on every call (section 3), and the model may recall them less reliably (context rot). A huge window raises the ceiling; it does not remove the cost or the recall problem.

Between sessions: nothing is kept unless you keep it 6 min

A session is one conversation, from the first message to the end. When it ends, the context is gone. Next week, when Maya asks about the 3D printer, a plain assistant has no idea she passed the laser-cutter training; she would have to say so again, or be trusted without proof.

The fix is memory: information stored outside the context window, in a file or database your program controls, and brought back into context when needed. Anthropic's name for the agent version is structured note-taking: the agent "regularly writes notes persisted to memory outside of the context window," and these notes "get pulled back into the context window at later times" (context engineering). A to-do list or a NOTES.md file are examples; this workspace's NOTES.md is one too.

How does an agent write a note? With a tool, like everything else. Anthropic's memory tool lets the model "create, read, update, and delete files that persist between sessions," but "Claude requests file operations, and your application runs them": "memory lives entirely in your application" (memory tool docs). This is the same loop you know: the model asks, your program acts. Two practical points from the docs: your code must restrict file paths to the memory folder, and the tool adds an instruction to look at the memory folder first on every new session.

A common mix-up

"The assistant will just remember students on its own." It will not: the model has no memory between sessions, and memory only exists if you build it. Also, memory is not free storage you dump everything into. Whatever you load back at the start counts against the window and the bill, so save short, useful facts (training status, preferences) and load only the ones the request needs.

Retrieval: finding the right page in a long manual 5 min

A laser cutter manual may run to hundreds of pages. A student asks, "What power setting for 3 mm acrylic?" You cannot put every manual in context (sections 3 and 4), and the model has not memorized your manuals. So the program looks up the relevant passage and puts only that into context. That is retrieval, and using it to ground an answer is often called retrieval-augmented generation (RAG).

The common pipeline has four steps, described in a survey as chunking, embedding, ranking and generation (RAG survey, arXiv):

  1. Chunk (once, ahead of time): split each manual into pieces, such as a section or a few paragraphs. Chunks should be "small enough to fit within a generation pipeline, and large enough to preserve semantic coherence"; a chunk cut mid-sentence or away from its table is hard to use (Microsoft, chunking).
  2. Embed (once): turn each chunk into a list of numbers, an embedding, built so that chunks with similar meaning get similar numbers. Store them in an index.
  3. Search (each question): embed the question the same way and find the closest chunks, typically by cosine similarity.
  4. Answer: return the top few chunks to the model as a tool result; it writes the answer from them.

There is also a choice about when to fetch. Anthropic describes just-in-time retrieval: the agent keeps "lightweight identifiers (file paths, stored queries, web links, etc.)" and uses tools to load data into context only when needed, rather than loading everything up front. Claude Code uses a hybrid: CLAUDE.md is loaded at the start, while search tools fetch other files on demand (context engineering). For your assistant, the safety rules suit "load up front"; the manuals suit "fetch on demand".

Retrieval can fail by returning the wrong chunk. If a chunk lost its heading ("Acrylic settings"), search may miss it. Some systems add document context to each chunk before indexing; that is a refinement for later.

Worked example and practice 7 min

Worked example: where does each item live?

Student Maya returns and asks: "Can I book the 3D printer Friday afternoon, and what nozzle should I use for flexible filament?" Decide where each piece of information lives.

  1. Assistant rules and tool descriptions: needed on every call, short, never change per student. They go in the context (system prompt and tool definitions), loaded every call.
  2. Maya's training status: personal, small, must survive between sessions. It lives in saved memory; at session start the program loads her one record into context.
  3. Friday's calendar: changes constantly. It is not stored; a tool fetches it fresh and the result sits in context for this request.
  4. Nozzle advice: lives in a long manual shared by everyone. It stays in the searchable index; search_manuals returns the two closest chunks into context.
  5. After booking: the program can clear the old calendar and manual results from context, and write one new line to Maya's notes ("booked printer Friday").

Cost: the context stays small (rules, one record, one calendar answer, two chunks), so every call is cheap, and nothing lives in the prompt that could live elsewhere.

Summary 2 min

  • The context window holds everything the model reads on a call: rules, tool descriptions, conversation and tool results. The model keeps nothing between calls.
  • Between steps, the program sends the history again, so cost grows with every result added; keep tool results small, and clear or compact when the context gets long.
  • Between sessions, only what your program saves survives; notes (memory) are written and read through tools, and loaded back selectively.
  • For long manuals, chunk and embed once, search per question, and put only the closest chunks into context.
