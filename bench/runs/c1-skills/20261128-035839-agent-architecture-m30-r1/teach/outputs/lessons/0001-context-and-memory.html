Context and memory: what your assistant can see and remember

By the end of this lesson you can decide, for any piece of information, whether your makerspace assistant should keep it in context, save it for later, or fetch it when needed, and explain what that choice costs.

Objective O3: context and memory in an agent About 30 minutes One-page cheat sheet
Why this matters for you

Your assistant has to answer from long machine manuals, remember each student between visits and stay within a small model budget. All three come down to one design question: what text goes into the model on each call? This is a good decision to be able to defend at your design review.

What it learned in training, and the text it is given as input. Training stops at some point, so anything newer or local, such as your makerspace's calendar, has to arrive in the input. Today is about managing that input.

Recall 2

Name the stages of the agent loop, from the goal to the end.

Check your answer

The model gets a goal and a set of tools. It asks for an action, the action is carried out, and the result goes back to the model. This repeats until the model gives a final answer or a limit is reached. Today's question: where do those results go, and how long do they stay?

1. The context window: what the model sees 5 min

Start with one request. A student types:

"The 3D printer shows error E05. How do I fix it, and is it free Thursday?"

(The error code and all the sizes in this lesson are made up for practice.)

The student wrote one sentence. The model receives much more than that. Your program assembles a bundle of text and sends all of it:

  • Instructions you wrote, often called the system prompt: "You are the makerspace assistant. Cite the manual page you used."
  • Tool definitions: the names, descriptions and inputs of tools such as search_manual and check_calendar.
  • The messages so far: the student's question, each tool request the model made, and each result your program sent back.

This bundle is the context. Its size is measured in tokens, the small chunks of text a model reads and writes. A token can be a single character or a whole word, and long words are split into several. A rough rule for English is about 4 characters per token, or 60 to 80 words per 100 tokens (Google's token guide). Exact counts differ between models, so treat this as an estimate.

The context window is all the text the model can reference while generating a response, including the response itself. The system prompt, tool definitions, messages and tool results all count toward it (context window documentation). It has a fixed maximum size that depends on the model.

Think of the window as your desk during an open-book exam. You can use whatever is on the desk. A book in the library down the hall does not help until someone brings the right page over.

That picture explains a lot. If the E05 fix is only in a PDF on your team's drive, and no step puts that text into the context, the model cannot read it. It may still write a confident-sounding fix from its training, which is the outdated-fact problem you have already noticed.

A common mix-up

"We gave the assistant the manuals, so it knows them." Storing files where your program can reach them changes nothing about what the model sees. Only text inside this call's context, plus training, can shape the reply.

2. Why the window fills up and costs money 6 min

Here is the fact that surprises most people. The model keeps nothing from one call to the next. An interface with this property is called stateless. One provider's documentation puts it plainly: you "always send the full conversational history" (working with messages).

Some services can store the history on their side for you. That saves your program some work, but the earlier text is still input to the model. For example, this conversation-state guide says earlier input tokens in a chain are still billed.

So the "memory" inside one conversation is a list that your program keeps and resends. In Python it looks like this. call_model and run_tool are placeholder functions, not a real library:

messages = [{"role": "user", "content": question}]

for step in range(MAX_STEPS):
    reply = call_model(SYSTEM_PROMPT, TOOLS, messages)
    messages.append(reply)       # keep what the model said
    if not reply.get("tool"):
        break                    # final answer
    result = run_tool(reply)     # your code runs the tool
    messages.append({"role": "tool", "content": result})

Notice the two append lines. The list only grows, and the whole list goes into the next call.

Two different numbers matter here:

  • Window use is the size of one call. The largest is 5,450 tokens plus the reply. This must fit under the limit.
  • Billed input is the sum over all calls: 12,600 tokens. This drives your input cost.

Suppose input costs $1 per million tokens (an invented price). One question costs 12,600 ÷ 1,000,000 × $1 = $0.0126. A thousand questions cost $12.60, before paying for output tokens.

Some providers offer prompt caching, a lower price for text that repeats from an earlier call. It changes what you pay, not how much of the window the text occupies (documentation).

Full is not the only problem

If a request is too large for the window, it can be rejected with an error, or the reply can be cut off when space runs out. What happens depends on the service and model (documentation).

Quality can slip before that point. As the number of tokens grows, a model's ability to accurately recall information from the context decreases. This is called context rot (Anthropic on context engineering).

A common mix-up

"Pick a model with a huge window and paste everything in." It is tempting because it needs no extra code. But every extra token is still billed, usually on every call, and more text can make the important line harder for the model to use. A bigger window raises the limit; it does not make filling it a good idea.

3. Between steps: what to keep 4 min

Your program builds the context, so your program decides what goes into the next call. Appending everything is the simplest choice, and it is fine for short tasks. For long ones, you need to edit.

The goal has a name. Context engineering means choosing and maintaining the best set of tokens for the model at each call. The guiding idea is to find the smallest set of high-signal tokens that gives you a good chance of the outcome you want (source). "High-signal" means text that actually helps with the next decision.

Imagine a student has been troubleshooting a print for 30 messages. There are three common moves.

Keep what the next decision needs

Keep the instructions, the current question, the recent exchanges and any fact still in play: the machine, the error code, the fixes already tried. Drop any of these and the assistant may ask again or repeat a failed fix.

Clear old tool results

An early search returned 3,000 tokens of manual text. The assistant used it long ago. Your program can swap that bulk for a one-line stub:

[Searched printer manual for "E05". Used p. 42:
 clear the nozzle. Full text removed.]

If the page is needed again, the assistant can search again. Clearing tool results is described as one of the safest, lightest forms of trimming (source).

Summarize and restart

Compaction means summarizing a conversation that is getting long, then starting a fresh context from that summary. A good summary keeps decisions, unsolved problems and important details, and drops repeated output. The risk is that aggressive compaction loses a subtle detail whose importance only shows up later (source).

Why choose one over another? Clearing a result removes a specific thing you can fetch again. Summarizing rewrites many things at once, and writing the summary usually takes a model call of its own. For short booking chats, you may need neither. Measure your conversation sizes before building either.

4. Between sessions: notes and saved memory 5 min

Maya asks about laser-cutting plywood on Monday. On Friday she returns: "Same material as last time. What settings?"

If Friday starts with an empty message list, the model has no idea what "last time" means. Something must have been saved on Monday and loaded on Friday.

Two terms separate these cases (LangChain's memory overview):

  • Short-term memory follows one conversation, or thread: mainly its message history. This is what sections 2 and 3 managed.
  • Long-term memory is user or application data kept across sessions and shared between conversations.

Long-term memory lives outside the context window, in a file or database. It affects a reply only when your program, or a tool the model calls, puts it back into the context.

Notes as memory

One approach is structured note-taking: the agent regularly writes notes to storage outside the window and pulls them back in later (source). A to-do list during a long task is one example. A small file per student is another.

{
  "student_id": "s-104",
  "usual_material": "3 mm plywood",
  "open_issue": "edges charred on last cut",
  "updated": "2026-11-23"
}

This single, updated record is called a profile. It is compact and easy to load, but updating it gets error-prone as it grows. The alternative is a collection: many small notes that you add to over time. It can capture more, but you must handle old or conflicting entries and search for the relevant ones (source).

When to write? Saving during the conversation makes the memory available at once but can add delay to the reply. Saving in a separate background job avoids that delay, but another conversation may start before the update lands (source).

Not everything belongs in notes

Training status decides who may use a dangerous machine. My design advice: read it from the official training record through a tool, each time it matters. A copied note can go stale, and a model-written note can be wrong. Save notes for things with no better home, such as a usual material or an unfinished problem.

Also decide what you will not store, who can see a student's notes, and how they get corrected or deleted. Load only the current student's record.

A common mix-up

"The assistant learned Maya's preference." It is tempting because Friday's reply looks like remembering. But the model did not change. Your program saved text and later put that text into the input. Delete the note and the "memory" is gone.

5. Retrieval: finding the right page 4 min

A 150-page manual at an assumed 400 tokens per page is 60,000 tokens. The E05 fix might be 300 of them. You want to bring only the useful part to the desk.

Retrieval means searching stored material and adding the relevant pieces to the context. When a model then answers using them, the pattern is called retrieval-augmented generation (RAG). A typical setup has two stages (Anthropic on contextual retrieval).

  1. Prepare: split the manuals into chunks, passages usually no more than a few hundred tokens, and index them for search.
  2. Query: find the chunks that best match the question and add them to the model's input.

Two kinds of search are common, and they can be combined (source):

SearchHow it matchesGood for
EmbeddingsTurns text into lists of numbers; similar meanings get nearby numbers"print won't stick" finding "poor bed adhesion"
Keywords (for example, the BM25 ranking method)Scores the words the texts shareExact codes and part names, such as "E05"

Watch for chunks that lose their meaning when cut out. "Set power to 40%" is useless, even risky, without the machine and material. Attach that information, such as "Laser cutter manual, plywood settings", to the chunk before indexing it (the same source studies this).

Retrieval can also happen just in time: the agent holds light references, such as file names or a search tool, and loads content only when it needs it (source). Your search_manual tool works this way. Notes can be fetched the same way, so retrieval and notes fit together: one finds information, the other stores what is worth finding later.

Retrieval has a cost too: you must build it, and it can return the wrong chunk. For a knowledge base under about 200,000 tokens, Anthropic notes you can simply include all of it (source). "Can" is about feasibility; your budget still gets a vote, as the worked example shows.

Worked example and your turn 3 min

Worked example: paste or retrieve?

You have three manuals of 60,000 tokens each. Should the E05 question carry all of them?

  1. Check that it fits. 3 × 60,000 = 180,000 tokens, plus about 2,000 fixed. Assume a 200,000-token window. It fits, with limited room for conversation and reply.
  2. Count the calls. With manuals pasted in, no search is needed. One call asks for the calendar and one writes the answer.
  3. Add up the input. Call 1: 180,000 + 2,050 = 182,050. Call 2: add 50 + 300 = 182,400. Total: 364,450.
  4. Price it. At the invented $1 per million, that is about $0.36 per question, against $0.0126 with retrieval: roughly 29 times as much.
  5. Weigh the rest. Caching could lower the price of the repeated manuals. Retrieval adds code and can miss a page. A fourth manual would overflow this window.
  6. Decide. Use retrieval, then test it with real student questions to see that the right page comes back.
Your turn

Maya returns and says: "Book the laser cutter Friday. Use the same settings as last time." Decide where each item should come from: in context already, saved note, live lookup or retrieval. Give one reason each.

  1. Her request just now
  2. The settings she used last time
  3. Whether her training is current
  4. Whether Friday is free
  5. The manual's safety rules for that material

Hint for item 1: it is part of this thread. Do the other four.

Show a solution
  1. In context: it is the current message.
  2. Saved note: it happened in an earlier session, so it exists now only if you saved it. If there is no note, the assistant should ask, not guess.
  3. Live lookup: the official record is current, and safety depends on it.
  4. Live lookup: bookings change, so call the calendar now.
  5. Retrieval: pull the relevant chunk, labeled with machine and material.

All five end up in the context in the end. The difference is where each is kept before that, and who vouches for it.

Summary 1 min

  • The context window holds everything the model can use in a call, plus its reply.
  • Your program resends the history, so large items are paid for repeatedly.
  • Between steps, keep what the next decision needs; clear or summarize the rest.
  • Between sessions, nothing carries over unless it is saved and loaded again.
  • Retrieval brings the right pieces in; notes keep what is worth finding later.

Say it in your own words: without looking, explain to a teammate how the assistant can "remember" Maya on Friday when the model itself keeps nothing.
